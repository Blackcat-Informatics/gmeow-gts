# Agent instructions

These rules apply to any automated agent working in this repository. `CONTRIBUTING.md` and
`docs/GTS-GOVERNANCE.md` apply as well; where this file is silent, they decide.

## When requests conflict

When requests conflict, these decide.

- **GREENFIELD:** we always correct the mistakes of the past. Others' mistakes are our
  lessons, not our limits.
- **SOTA:** always choose the state of the art over the bones of the past.
- **OPTIMAL:** choose the Pareto frontier of the quality, speed, efficiency and other axes.
- **MAXIMAL:** support the broadest functionality possible after the other choices are made.

## What this repository is

This repository holds the standard for GTS: the specification (`docs/GTS-SPEC.md`), the
conformance corpus (`vectors/`) and independent reference engines in several languages. It
stands alone. Its engines exist to prove the specification can be implemented from the text
and to give every other implementation a second one to be checked against; they are not a
dependency of any particular product.

Three consequences follow:

- The specification and the corpus are the contract. An engine that disagrees with them is
  wrong, and a corpus file that disagrees with the specification is a defect to report.
- No engine here may be bent to suit one consumer. A need that only one consumer has belongs
  in a profile, not in the core format.
- Agreement between this repository's engines and an outside implementation is evidence.
  Never weaken a vector or an engine check to make another implementation pass.

## Format generations

- Engines write the current format generation only.
- Readers keep reading older generations, in code, for as long as files of that generation
  may exist.
- When a generation breaks compatibility, a conversion command is provided, and converted
  data is shown equal to its source by content before anything is discarded.
- A reader that meets a generation it does not implement refuses loudly. It never guesses.

## Changing the format

- Any change to the grammar, the hash or signature preimages, the fold, or the conformance
  tiers goes through the proposal process in `docs/GTS-GOVERNANCE.md` before it is merged.
- A specification change lands together with its vectors. Keep the specification, the
  `ietf/` draft, the translations under `docs/i18n/` and `docs/documentation-roster.json`
  consistent in the same change.
- The corpus is generated by the Python reference engine
  (`python/scripts/gen_vectors.py`). After any change that could affect bytes, regenerate it
  and confirm that files you did not mean to change are byte-identical.
- A dependency update that touches a serialization, hash, signature or compression library
  needs evidence that written bytes are unchanged: the corpus regenerates identically, or a
  before-and-after comparison of engine output.

## Verification

- Prove a claim with the narrowest command that proves it: one test file, one package, one
  command-line invocation. The per-engine commands are in `CONTRIBUTING.md`.
- Do not run every engine's full suite as a ritual. Run the engines your change touches, and
  let the hooks and continuous integration run what they are configured to run.
- Report what was run and what was not. A check that was skipped is stated as skipped.
- A new test protects a named behaviour, regression, boundary or invariant. Stop adding
  tests once the contract is covered.

## Commits and merges

- Commit hooks are never bypassed, by any option or environment variable. If a hook fails,
  fix the cause.
- Do not add tool branding, agent credits, signatures or co-author trailers to commits,
  issues, pull requests or files.
- This repository is public. Nothing private goes into a commit message, an issue, a pull
  request or a tracked file: no names of unpublished projects, no local paths, no
  conversation contents.
- A pull request is merged only when every required check has passed on its current head.

## Shell conduct

1. One shell call does one thing. Do not chain long sequences with `&&` or `;`. A longer
   sequence is written to a script file and run as a file.
2. A deletion is never part of a chain. It is its own call, names one exact path inside
   this repository, and that path was listed in an earlier call. Remove worktrees and
   branches with `git worktree remove` and `git branch -d`, never with force.
3. Do not delete by glob or by variable, do not write outside this repository, and do not
   resend a refused command in another form.
4. Do not poll or sleep while waiting. Run a long command in the foreground with a timeout,
   or in the background and act when it finishes.

## Scratch space

Working files, logs, measurements and drafts go under `.stage/`, and additional checkouts
under `.worktrees/`. Both are ignored by Git and are never committed. Do not use the system
temporary directories.
