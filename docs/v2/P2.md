# Part P2: Registry

## 1. Scope and dependencies

This part is the one authority for every enumeration of the format, for the finding table and the `reason` enumeration, for
the registry versions, for the table of hash contexts and for the mandatory algorithm set. It assigns the codes. It does not
define what a code means to the part that uses it: the field that carries a value, the rule that produces a finding and the
procedure that checks a claim belong to the part named beside each value. A requirement of this part whose subject is the
registry, a
registry version, a table or a profile binds the change controller of section 9a and every later revision of this part.

Depends on: nothing. Every other part depends on this one.

Notation. The typed notation is that of `P1` ("The typed model and its one serialization"): `uint`,
`bool`, `bytes`, `text`, `digest`, `enum(E)` (a `uint` that is a code of enumeration `E`), `list(T)`, `option(T)`, records
as arrays of fields in declared order and variants as arrays whose first element is a tag. `E(x)` is the deterministic
encoding of `x`. A label in backticks (for example `quad`) names a value of an enumeration in this document and in the other
parts; it is never a wire value.

The labelling specification of blank nodes is cited as `L1` and by the name of its section. Where this part says "registry version
`1`", it means the values of sections 4 to 6 and 8 (`P2-13`).

REQUIREMENT LANGUAGE. The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT",
"RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14
[RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here. This document uses the key words MUST,
MUST NOT and MAY, and no other.

## 2. Conventions of every enumeration

1. `P2-1` Every enumeration of the registry MUST have codes that are dense from `1`: the code `0` MUST NOT be assigned to any
   value, and every integer from `1` to the highest code MUST be assigned.
2. `P2-2` A field of type `enum(E)` MUST be encoded as the `uint` code of its value and decoded by that code alone. No rule of the
   format reads a label, and no outcome of the format depends on a spelling or on the size of a code.
3. `P2-3` The tag of a variant MUST be a code of the variant's tag enumeration named in table 4.4. A tag that is not a code
   of that enumeration in the reader's registry version is `malformed_value` with reason `unregistered_value`, except where
   section 7 gives another result, and except the tag of a `mark` and of a `mark_target`, which `P1`, "The resync item", judges:
   such a tag that is not a code of the reader's registry version, or is `0`, makes the mark not applicable and is no finding.
4. `P2-4` The codes of `L1`, which begin at `0`, are values of `L1` and are not rows of this registry; the format stores none of
   them (the index holds no labelling record and no refusal is stored).

The codes that `L1` uses inside its own encodings (the line tags `0x40` to `0x44`, the last being the `record` kind) occur
only inside `L1` encodings. The enumeration `line_kind` of this registry has the format's own codes (table 4.3) and is never
mixed with them.

## 3. Registry versions

A registry version is a `uint` from `1`. The version that a segment declares is the header's `registry_version`; the version
that a reader implements is the `registry_version` of its result.

1. `P2-5` A registry version MUST be a `uint` of at least `1`. A header whose `registry_version` is `0` is `malformed_value` with
   reason `out_of_range`.
2. `P2-6` Version `n`, for `n` above `1`, MUST hold every value of version `n - 1` with its code and meaning unchanged, and MUST
   add at least one value or retire at least one algorithm; it MUST NOT change, renumber or remove a value, and it MUST NOT change
   the columns, the envelope rules or the shape
   of the content record (the number and the types of its elements) of a frame type that an earlier version defines.
3. `P2-7` A value that version `n` adds to an enumeration MUST take the next integers above the highest code that enumeration has
   in version `n - 1`, in the order of acceptance of the proposals that add them (section 9a), the adding part listing them in
   that order, so that the enumeration stays dense (`P2-1`).
4. `P2-8` A reader that implements registry version `n` MUST implement every value of every enumeration of versions `1` to
   `n`: each code decodes to its value and each value has the meaning its part gives it.
5. `P2-9` A reader that implements registry version `n` MUST implement every frame type of versions `1` to `n`: its content
   record, its fold or durability role, its checks and its `critical` and `transparent` columns.
6. `P2-10` A reader that implements registry version `n` MUST implement every algorithm and codec of versions `1` to `n`
   (section 8 for version `1`).
7. `P2-11` A reader that implements registry version `n` MUST produce every finding code, with its severity, its reasons and its
   present fields (section 5), that versions `1` to `n` define, and MUST implement every row of the hash context table (4.6).
8. `P2-12` No clause of the format leaves the implementation of a value of a version to choice. A claim that a reader implements a
   registry version MUST NOT be qualified by an exception (the conformance claim is defined by `P7`).
9. `P2-13` Registry version `1` is the core: it is exactly the values of sections 4 to 6 and 8 of this part.
10. `P2-14` A further algorithm MUST be added only as a new registry version, by the allocation of section 9a, and every
    conforming reader of that version MUST implement it in full (`P2-8` to `P2-11`). A profile is not a registry version and never
    raises a header's `registry_version` (section 9).
11. `P2-15` The `registry_version` of a header MUST be the smallest version that holds every enumeration value, frame type,
    algorithm and codec that the segment uses, the codes of a mark excepted (`P1`, "The resync item"). The canonical check
    compares it (`P7`).

What implementing a version in full means, stated once. A reader of version `n` has no value of versions `1` to `n` that it
decodes as unknown. Two readers of one registry version and one stated capacity reach the same result from the same bytes and the
same
inputs of the read that `P2-65` names (`end` under `forward`, the query under `sparse`, and one failed read when one occurred),
which is why the version, and the capacity of the reader (`P7`), are fields of its result.

Version `2` is assigned by the sealing part (`P8`), which lists every value of it but the enumeration
`sealing_refusal_reason`, which section 9 of this part lists.

A segment that declares a version above the reader's gives the finding `unsupported_registry_version`; what the reader then
does is section 7.

### 4.6 The hash context table

The construction `H_ctx(context, message)` is defined by `P1`: the key-derivation mode of the hash named by `hash_algorithm`
with the spelling of the context as its context string and the message as its key material. This table is the one list of
contexts of the core. `code` and `label` name the row in this registry and in the other parts; `spelling` is the ASCII
string that is hashed. The contexts that `L1` uses inside its own hashes are `L1`'s and are not rows.

| code | label | spelling | the message it hashes (defined by) |
|---|---|---|---|
| 1 | `header` | `gts2 header` | `E(header)` (`P1`) |
| 2 | `frame` | `gts2 frame` | `E(identity)` (`P1`) |
| 3 | `payload` | `gts2 payload` | the decoded payload bytes (`P1`) |
| 4 | `stored` | `gts2 stored` | `E([codec])` then the stored payload bytes; the stored check is the first 16 bytes (`P1`) |
| 5 | `unit` | `gts2 unit` | the bytes of a chunk, blob or value (`P4`) |
| 6 | `range_leaf` | `gts2 range leaf` | `E([identifier])` of the effective identifier (`P5`) |
| 7 | `range_node` | `gts2 range node` | `E([left, right])` (`P5`) |
| 8 | `range_root` | `gts2 range root` | `E([count, peaks])` (`P5`) |
| 9 | `shard` | `gts2 shard` | one parity shard; the shard digest is the first 16 bytes (`P5`) |
| 10 | `parity_table` | `gts2 parity table` | `E([h0, data_shard_digests, parity_shard_digests])` (`P5`) |
| 11 | `signature_subject` | `gts2 signature subject` | `E(subject)` (`P6`) |
| 12 | `key_id` | `gts2 key id` | `E([algorithm, public_key])` (`P6`) |
| 13 | `gear_table` | `gts2 gear table` | the empty message; the extended output is the chunker's table (`P4`) |
| 14 | `source_bytes` | `gts2 source bytes` | the bytes of a whole first-generation source file (`P9`) |
| 15 | `nested_term` | `gts2 nested term` | `E([K(s), K(p), K(o)])`, the sources of the components of a nested term, and `E([ordinal, label])` of a blank node that is such a component (`P3`) |

1. `P2-24` The spellings of the table MUST be hashed whole, exactly as written (the ASCII bytes of the text between the
   backticks); no outcome of the format depends on any property of a spelling other than its bytes.
2. `P2-25` The code of a row MUST NOT enter any hash, preimage or wire field; the spelling is the only part of a row that does.
3. `P2-26` The table MUST be the only list of contexts of the core, and the spellings MUST be pairwise different.
4. `P2-27` Version `2` adds its rows to this table, with codes that continue from `16` (`P2-7`); `P8` defines them.

### 4.8 The records of the resync item and of the marks

Each record is a CBOR array in the deterministic form of `P1`; the rules of its fields, its sizes and its identifier are those of
`P1`, "The resync item". The enumerations it uses are those of 4.1 and 4.5 and of sections 5 and 6.

```text
resync = [ item_kind: enum(item_kind),        ; element 0: `resync` (5)
           generation: uint,                  ; element 1: 2
           marker: bytes,                     ; element 2: the 16 bytes of the marker
           registry_version: uint,            ; element 3
           hash_algorithm: enum(hash_algorithm),   ; element 4
           profile: option(enum(profile)),    ; element 5
           lineage: option(lineage),          ; element 6
           offset: uint,                      ; element 7
           past: option(digest),              ; element 8
           marks: list(mark),                 ; element 9: at most 64
           identifier: digest ]               ; element 10
mark = [1, target: mark_target, strains: enum(capacity_field), measures: list(measure)]            ; hostile
     / [2, target: mark_target, finding: enum(finding_code), reason: option(enum(reason)), count: uint]   ; observed_defect
     / [3, target: mark_target]                                                                         ; filler
mark_target = [1] / [2, offset: uint, length: uint]
measure = [ field: enum(capacity_field), value: uint ]
```

The reader's input for marks, the field `marks` of the result of a read, is `option(limits)`:

```text
limits = [ stored_bytes_per_frame: uint, decoded_bytes_per_frame: uint, labelling_units: uint, labelled_lines: uint,
           decoded_bytes_per_read: uint, rebuilt_bytes_per_read: uint, formed_bytes_per_read: uint,
           labelled_bytes_per_read: uint ]
```

The fields that the typed result gains are `opener` of a segment result (`opener_kind`, 4.7), `marks` of a read result
(`option(limits)`), `end` of a file result of tag `2` (`file_end`, 4.7) and `left_out` of a file result of tag `2` (a `uint`: the
count of frames and items left out of the fold, `P7`); they are defined in `P7`. `left_out` and `marks` register no enumeration.

1. `P2-100` The tag of a `mark` and the tag of a `mark_target`, and the codes `strains`, `field`, `finding` and `reason` of a
   mark,
   are judged by `P1`, "The resync item", and by no rule of this registry (`P2-3`, `P2-15`, `P2-57`, `P2-63`): a mark with a tag

## 5. The finding table

A finding is the record
`finding = [code: enum(finding_code), reason: option(enum(reason)), subject: option(subject_kind), position: option(uint),
offset: option(uint), length: option(uint), count: option(uint)]`
(its place in the result is defined by `P7`). Its severity is not a field: it is the fixed column `severity` of its code. A code
means one kind of event. The column `reasons` lists the values of the one `reason` enumeration (section 6) that the code allows;
`none` means the `reason` field is `absent`.

ONE EVENT, ONE REASON. A finding carries one reason. When two reasons of one code apply to one event, the finding carries the
first of them in the order of the procedure of the part that produces it, and that part states the order; where a code has no such
procedure the table of 6.1 is the order, by ascending code. The findings of one list stand in the order that `P7` defines
("Where each finding stands, and in what order").

### 6.4 Requirements

1. `P2-51` Registry version `1` MUST define exactly the 92 reasons of the table in 6.1, with those codes, and a reader of registry
   version `1` MUST NOT report any other reason.
2. `P2-52` A label that two lists name MUST be one value of `reason` with one code; the code of a reason MUST NOT depend on the
   finding it qualifies.
3. `P2-53` The `reason` of a signature result MUST be `absent` for the status `valid`, one of the eight invalid reasons of 6.2 for
   the status `invalid`, and `unknown_signature_algorithm` or `key_not_held` for the status `unverified`.
4. `P2-54` A reason that has a subject MUST NOT have the subject inside its label: the subject is the `subject` field of the
   finding (`P2-46`, `P2-47`).
5. `P2-55` A value that a later registry version adds to `reason` MUST take the next integers above the highest code in the
   previous version, in the order of acceptance of the proposals that add them (`P2-7`, section 9a).
6. `P2-79` The reason `refusal_size` MUST be reported only for a fold whose size, as `P3` "Refusals and the reader's limit"
   defines it, exceeds the reader's `labelled_lines`, and MUST be reported before any record is built; it has no subject.
7. `P2-82` A finding of code `exceeds_capacity` MUST have `position` present, naming the frame, for the reasons `decoded_size`,
   `stored_size`, `total_decoded`, `total_formed` and `total_rebuilt` (for `total_rebuilt` the frame that holds the declaration:
   the pack frame
   for a member, the sealed frame for a member of a sealed pack; for the reason `total_decoded` given for the charge of a resync
   candidate (`P1`, "Finding a resync item where framing is lost") no frame exists, and `position` is the position of the item in
   which the occurrence begins, or, when it begins in bytes that cannot be delimited or in an incomplete item, the position that
   the next item would have; the `offset` is that of the occurrence and the `length` is `4096`; the finding stands in the segment
   before the accepted item, in the last segment when none is accepted, or in the findings of the file, with the `position`
   `0`, when the file has no segment), and `position` absent for the reason `item_count`; for `item_count` the
   `offset` MUST be the offset of the first byte not read and the `length` the number of bytes from there to the end of the input.
   A reason that registry version `2` adds to this code states its own fields in `P8`.
8. `P2-83` The reason `total_decoded` MUST be reported only for a frame that `P1` "The payload check" judges at its third
   capacity step or for the charge of a resync candidate by `P1`, "Finding a resync item where framing is lost", the reason
   `item_count` only by the step FRAMING of `P7`, when `items_per_read` items have been delimited and
   a byte of the input remains, and the reason `total_rebuilt` only by the step UNITS AND VALUES of `P7`, once for each
   declaration that `P4` "The total rebuilt length" refuses; none of the three has a subject.
9. `P2-97` The reason `refusal_weight` MUST be reported only for a fold whose size is admitted and whose weight, as `P3`
   "Refusals and the reader's limit" defines it, brings the total labelled weight of the read above the reader's
   `labelled_bytes_per_read`, or that follows such a fold, and MUST be reported before any record is built; it has no subject.
10. `P2-99` The reason `refusal_term_node` MUST be reported only for a fold whose size and weight are admitted and that holds two
    different nested terms with equal digests, as `P3` "Nested terms, lowering and term nodes" defines them, and MUST be reported
    before any record is built; it has no subject.
11. `P2-98` The reason `total_formed` MUST be reported only for a `terms` frame whose charge, as `P3` "Front coding" defines
    it, brings the total formed length of the read above the reader's `formed_bytes_per_read`, or that follows such a frame;
    its `position` names the frame, and it has no subject.
12. `P2-84` A reader MUST give a finding for which two reasons of its code apply to one event the first of the two in the order of
   the procedure of the part that produces it, as that part states it, and MUST NOT report the event twice with two reasons unless
   that part says that it gives one finding for each; where a code has no such procedure the order MUST be that of the table of
   6.1, by ascending code.

## 7. A value against the registry versions

Let `h` be the `registry_version` of the segment's header and `r` the registry version the reader implements (section 3). A
reader judges every value of a segment by one rule, chosen by comparing `h` with `r`; it never guesses a meaning.

| case | rule | what it fixes |
|---|---|---|
| the code `0` in any enumeration field | `P2-63` | `malformed_value`, `unregistered_value`, whatever `h` and `r`; in a content record at its place and only for a frame whose link state is `linked` or `healed`; the codes of a mark are judged by `P1`, "The resync item" |
| `h` at most `r` | `P2-57` | every value judged against version `h`; the codes of a mark are judged by `P1`, "The resync item" |
| `h` above `r` | `P2-56` | one finding for the segment, then the rows below |
| `frame_type`, `critical` false (`h` above `r`) | `P2-58` | opaque frame, the fold continues |
| `frame_type`, `critical` true (`h` above `r`) | `P2-59` | the fold of the segment stops |
| `codec` or `storage` tag (`h` above `r`) | `P2-60` | payload `unchecked` with `unknown_codec` |
| `signature_algorithm` (`h` above `r`) | `P2-61` | status `unverified`, one finding |
| other enumeration or tag in a content record (`h` above `r`) | `P2-62` | the frame is a frame of unknown type, judged at the place of its field in the record and only when its link state is `linked` or `healed` |
| `item_kind` (`h` above `r`) | `P2-64` | opaque item, delimited and counted |
| `profile` of the header | `P2-21` | any `h` and `r`: judged by the profile table alone |

1. `P2-56` When `h` is above `r`, a reader MUST report `unsupported_registry_version` once for the segment; MUST delimit and
   count every item; MUST check the link of every frame when it implements the header's `hash_algorithm` and otherwise check
   no link and fold nothing; MUST keep a header `canonical` value it does not hold and read the segment (the `profile` is
   read by `P2-21`); MUST treat every other value it does not know by `P2-58` to `P2-62` and `P2-64`, calling nothing
   malformed for being unknown; MUST fold what it can; and MUST report each frame it did not fold as opaque with its reason.
2. `P2-57` When `h` is at most `r`, a reader MUST judge every value of the segment against version `h`. A value that is not
   in version `h` but is in a later version that the reader implements MUST be reported `malformed_value` with
   `forbidden_combination`; a value that is in no version the reader implements MUST be reported `malformed_value` with
   `unregistered_value`. For a field of the header either report makes the header unreadable, so that the items of the
   segment are delimited and counted only; this holds for an unknown `hash_algorithm`, which is this `malformed_value` and
   not `unsupported_registry_version`. For any other field the frame that holds it is opaque with `malformed`; a value of a
   content record is judged by the part that defines the type, in the step that `P1`, "The record, in identity order", ORDER OF
   THE FIELD CHECKS, gives it, and only for a frame whose link state is `linked` or `healed`. The header's `profile` is judged
   by `P2-21` and not by this rule, except for the code `0` (`P2-63`). A code of a mark is judged by `P1`, "The resync item",
   and not by this rule.
3. `P2-58` When `h` is above `r`, a frame whose element 1 is a `frame_type` value (`P1`, "The locator", A FRAME ITEM HAS A TYPE
   ONLY BY A VALUE) that is not a code of the reader's version, whose `critical` is false and whose `transparent` is a `bool`
   MUST have its link checked, MUST be reported `unknown_enumeration_value` with reason `unknown_frame_type` and subject
   `[2, frame_type]`, MUST be reported opaque with `unknown_frame_type`, and the fold MUST continue.
4. `P2-59` When `h` is above `r`, a frame whose element 1 is a `frame_type` value (`P1`, "The locator", A FRAME ITEM HAS A TYPE
   ONLY BY A VALUE) that is not a code of the reader's version, whose `critical` is true and whose `transparent` is a `bool`
   MUST have its link checked, MUST be reported `unsupported_critical` with subject `[2, frame_type]`, MUST stop the fold of the
   segment at that frame, and every later frame of the segment MUST be reported opaque with `stopped`, its link still checked. A
   frame of type `parity` is never such a frame: a `critical` that is true on it is damage (`P2-67`). A frame item of no frame
   type (`P1`, "The locator") is judged by neither `P2-58` nor `P2-59`: its finding is the `malformed_value` of `P1`, no
   `unsupported_critical` is reported for it, and it stops no fold. A frame of a type that the reader does not know whose
   `critical` or `transparent` is not a `bool` is judged by neither as well: only its `malformed_value` is reported, and it
   stops no fold (`P1`, "Values the reader does not know").
5. `P2-60` When `h` is above `r`, a frame whose `codec` is not a code of the reader's version, or whose `storage` tag is not
   a code of `storage_kind`, MUST be reported with `payload_state` `unchecked` and `unknown_codec` and with
   `unknown_enumeration_value` with reason `unknown_codec` and subject `[1, codec]` (the value in the subject is the tag code
   when the tag is not a code of `storage_kind`, and otherwise the codec code); its link and stored check MUST still be checked;
   and it MUST NOT be folded: a frame of a content
   type is reported opaque with `unknown_codec`. On a frame of type `parity` an unknown codec or storage tag is damage
   (`P2-67`), in a segment of any registry version, and never `unknown_codec`.
6. `P2-61` When `h` is above `r`, a signature whose `signature_algorithm` is not a code of the reader's version MUST be reported
   with status `unverified` and reason `unknown_signature_algorithm`, its `key_id` kept, and exactly one finding,
   `signature_unverified` with that reason and subject `[3, signature_algorithm]`; `unknown_enumeration_value` MUST NOT be
   reported for it.
7. `P2-62` When `h` is above `r`, a frame whose content record holds an enumeration value or tag that the reader does not know
   MUST be treated as a frame of unknown type: as `P2-59` when its `critical` is true and as `P2-58` when it is false, with the
   subject `[2, frame_type]` of the frame type of its envelope. The value
   is judged at the place of its field in the order of the fields of the record, after the field rules of `P1` and after the
   payload has verified (`P3`, "The order of the payload checks"), so that a violation of an earlier field comes first and gives
   its `malformed_value` instead; and it is judged only when the link state of the frame is `linked` or `healed`: the content of
   a frame whose link is `broken` is not interpreted, and the frame has its `chain_break` and no `unsupported_critical` and no
   `unknown_enumeration_value` from such a value. A frame of type `parity` is judged for the shape of its content record first,
   in a segment of any registry version: a record that is longer, shorter or ill typed is damage (`P2-67`), whatever values it
   holds (`P1`, "Values the reader does not know"). Only when the envelope is as the type states, the content record has the
   shape the reader holds, the link state is not `broken`, and an enumeration value in it (a `geometry`) is one the reader does
   not hold, is the frame opaque with `unknown_enumeration_value` and reason `unknown_frame_type`, not used, with the fold
   continuing and no `parity_damaged`.
8. `P2-63` The code `0` is not a value of any registry version (`P2-1`); in every enumeration field and every variant tag it MUST
   be reported `malformed_value` with reason `unregistered_value`, whatever `h` and `r` are, a frame of type `parity` excepted,
   in which it is damage (`P2-67`), and the codes of a mark excepted, which `P1`, "The resync item", judges. In a content
   record the code `0` is judged at its place in the order of the fields of the record, in the step of the part that defines the
   type, and only for a frame whose link state is `linked` or `healed`. The rows of this
   section apply to
   codes of at least `1`.
9. `P2-64` When `h` is above `r`, an item whose `item_kind` is not a code of the reader's version MUST be an opaque item,
   delimited and counted, reported `unknown_enumeration_value` with reason `unknown_item_kind` and subject `[5, item_kind]`. An
   item of a kind that is not a code of registry version `1` fails the framing test of `P1`, "Finding a resync item where framing
   is lost", in a segment whose opener is `readable` and states `registry_version` `1`, and does not fail it in any other
   segment, whatever `r` is; this decides which bytes that section scans and changes no result of this requirement.
10. `P2-65` For one registry version and one stated capacity, and under the access `forward` one value of `end` and under
    the access `sparse` one query, and one failed read when one occurred, two conforming readers MUST give the same result from
    the same bytes and the same other inputs of the read (the profiles they implement, the claim `readers`, `marks`, the inputs
    of a verifier and, in registry version `2`, the sealing input) (`P2-8` to `P2-12`). This holds for a `refusal_limit` of the
    labelling as for every other result: the labelling
    specification
    defines it as a function of the labelled set as given and of the capacity (`P3`). The reader's
    registry version and capacity are fields of the result so that any difference is explained.
11. `P2-66` The enumerations `option_tag` and `severity` are closed: no registry version adds a value to them. `item_kind`
   and `storage_kind` can gain values in a later version (`P2-6`), and then `P2-60` and `P2-64` apply to them; this never
   changes what the type `parity` states for its own `storage`, which is `stored_plain`.
12. `P2-67` A frame of type `parity` is written with `transparent` true, `critical` false, `stored_plain` and no signature;
   a frame of that type read with another value of one of these envelope fields, or with any other damage, in a segment of
   any registry version, MUST be reported `parity_damaged` and no other finding of `P1` (`P1`, "The record, in identity
   order"), outside the case of `P2-62`, so that damage to the repair layer never voids the file it protects. A frame whose
   envelope field `transparent` is true MUST NOT enter `integrity_state`, which is a function of the ordinary frames only.

## 8. The mandatory algorithm set

Registry version `1` has one algorithm set for each purpose. Every reader of version `1` implements every member (`P2-10`). The
set is closed: no member can be left out, no value is private, and no alias exists for a member. A member can be RETIRED by a
later
registry version (section 9a); retiring removes nothing and no member is retired in versions `1` and `2`.

| purpose | members in version `1` | retired from |
|---|---|---|
| hash | `blake3_256` (code `1` of `hash_algorithm`) | none |
| signature | `ed25519` (code `1`) and `mldsa65_ed25519` (code `2`) | none |
| compression | `zstd` (code `1` of `codec`) | none |
| sealing cipher and key wrap | none in version `1`; one of each in version `2`, defined by `P8` | none |

### 8.1 Why each member is in the set (informative)

`blake3_256`. `L1` fixes the BLAKE3 hash for its digests and identities (`L1`, under the heading "The whole input: order,
result, record, identity, map, guarantee, outcomes, hash", the paragraph "THE HASH, THE IDENTIFIER AND THE SECURITY
ASSUMPTION"). One hash makes the content digest, the identifiers and the labelling agree, so no file has two hashes for one
purpose. The one cost of the choice is stated here and nowhere else: an environment confined to another approved hash cannot
write or check files of this version (`L1`, the same paragraph). The digest length is 32 bytes, and every context of 4.6 is
hashed in the key-derivation mode of this hash.

`ed25519`. The classical scheme of RFC 8032 (Edwards-Curve Digital Signature Algorithm (EdDSA), January 2017), the most
widely implemented, with signatures of 64 bytes and public keys of 32 bytes. It has one strict verification policy (`P6`).
Its small size suits a signature on every commit, where the composite below is large (its signature value is 3,373 bytes).

`mldsa65_ed25519`. The composite construction with label `COMPSIG-MLDSA65-Ed25519-SHA512` and prefix
`CompositeAlgorithmSignatures2025`, which pairs ML-DSA-65 (FIPS 204, Module-Lattice-Based Digital Signature Standard, August
2024) with Ed25519 (RFC 8032) and the hash SHA-512 of FIPS 180-4 (Secure Hash Standard, August 2015). Its reason is
post-quantum protection that also holds while either half holds: a forgery needs both halves to fail. Its value is the
ML-DSA signature of 3,309 bytes followed by the Ed25519 signature of 64 bytes, 3,373 bytes in all; its public key is 1,952
bytes followed by 32 bytes. Pure post-quantum schemes and hash-based schemes are not in version `1`: each would be a second
member for a purpose that has one, with no stated need beyond the composite. `P6` defines the construction byte for byte.

`zstd`. It is used within the constraint of the envelope (`P1`): one frame a payload, whose header is the one that
`decoded_length` gives, with the content size recorded, no checksum, no dictionary and a window of at most `2^26` bytes.

1. `P2-68` A reader of registry version `1` MUST implement `blake3_256`, `ed25519`, `mldsa65_ed25519` and `zstd`.
2. `P2-69` Registry version `1` MUST NOT hold another hash algorithm, signature algorithm or codec, and MUST NOT hold an alias,
   a private-use value or an algorithm of choice for any purpose.
3. `P2-70` A conforming reader MUST NOT report a result for a file that differs because an implementation lacks one of these
   members; an implementation that lacks one MUST NOT claim registry version `1`.
4. `P2-71` A segment of registry version `1` MUST declare `hash_algorithm` `blake3_256`.
5. `P2-72` The value of a signature of `mldsa65_ed25519` MUST have exactly 3,373 bytes and its public key exactly 1,984 bytes, and
   the value of a signature of `ed25519` exactly 64 bytes and its public key exactly 32 bytes; any other length is the reason
   `value_length` (`P6`).

## 9a. Allocation, the record, withdrawal and retirement

THE AUTHORITY. A code of any numeric table of this part (every enumeration of sections 4 to 6 and 9, the finding table, the
`reason` enumeration, the `profile` table, the hash contexts, a registry version) is assigned by the proposal process of the
maintainers of this specification, and by no other body. A PROPOSAL is a request to add, withdraw or retire a value; it is
ACCEPTED when the maintainers adopt it. An implementation, a profile author, a deployment or a proposer assigns no code. The
CHANGE CONTROLLER of the tables is the maintainer body that accepts proposals under that process. A proposal that adds an
algorithm or a codec states its security
considerations.

THE RECORD. The tables of this part are the record of the assigned codes, and the ASSIGNMENT LOG of this section is the record
of which proposal assigned each one. The log has one row for each accepted proposal that adds, withdraws or retires a value, with
the
proposal's identifier, the registry version that holds the value
(or `profile` for the profile table), the enumeration, the codes, and the status `assigned`, `withdrawn` or `retired`. A row is
added when the proposal is accepted. While the registry version of a row is open, the row changes with the codes it records
(CONCURRENT PROPOSALS, AN ERRONEOUS ASSIGNMENT); from the release that closes that version it is never edited or removed. The
log is published with the specification.

| proposal | registry version | enumeration | codes | status |
|---|---|---|---|---|
| none: the values of sections 4 to 6 and 8 | 1 | every enumeration of those sections | as listed | assigned |
| none: the values that `P8` lists | 2 | as `P8` lists | as `P8` lists | assigned |

CONCURRENT PROPOSALS. A proposal names the values it adds by label only. A code written in a proposal has no standing. The code
of a value is written when the proposal is ACCEPTED: the change that adds the value to this part LANDS, becoming part of
the published text, and the codes are the next integers above the highest code of the enumeration at that moment (`P2-7`). The
order
of acceptance is the order of landing, which is a total order, so two proposals that want the next code never receive the same
one: the first to land receives it and the second receives the following integer. A proposal that lands later and has been
written against a code already given is changed to the following integer in the same change. A
code is PROVISIONAL while the registry version that holds it is open, and PERMANENT from the release of the specification that
publishes that version.

WHICH REGISTRY VERSION HOLDS A VALUE. Each value is held by exactly one registry version, the one named in its log row. A registry
version is OPEN until the release of the specification that names it as published, and CLOSED from that release. While a version
is open its values and codes can still change: a code can be renumbered, and a value assigned in error can be removed, the codes
above it being renumbered so that the enumeration stays dense (`P2-1`), in one change. No
implementation of an open version conforms: a claim of registry version `n` (`P7`, "Conformance") is a claim of a closed
version. From the release that closes a version, no value is added to it, removed from it or renumbered in it (`P2-6`). The
first value or retirement accepted after a version is closed opens the next version number, and every value accepted until that
version is
closed belongs to it. A reader finds the version of a value in the log and implements it by `P2-8` to `P2-11`.

AN ERRONEOUS ASSIGNMENT. A value assigned in error while its registry version is open is removed, as WHICH REGISTRY VERSION
HOLDS A VALUE states, and its log row with it. A value assigned in error in a closed version is not removed, not renumbered and
not given another meaning, and its code is never reused (`P2-1`, `P2-6`). It becomes WITHDRAWN: a log row with the status
`withdrawn` names the registry version from which it is withdrawn. A withdrawn value keeps its meaning for a reader (`P2-8`),
and a writer does not write it from that version.

NO PRIVATE OR EXPERIMENTAL RANGE. The registry has no private-use range, no experimental range and no reserved gap, because the
codes are dense from `1` (`P2-1`, `P2-69`). What follows: (a) an experiment that needs a value is a proposal that is not yet
accepted
and names its values by label; it runs on a reader that implements the draft and is not a conforming reader of any
registry version; (b) a file that holds a code the reader's registry does not assign is read by section 7 and is not a file of
any published version; no implementation claims to read it; (c) content that needs a vocabulary of its own uses an RDF
vocabulary in its content (`P3`, "Metadata is RDF"), which needs no code, and a domain profile is such a vocabulary with its own
checks outside this registry; a header's `profile` field holds only a code of the `profile` table. A code is never used before
it is assigned.

THE CHECKS OF A PROFILE. A profile document numbers its checks from `1` and a later revision appends checks (`P2-23`). A reader
implements a profile at a number of checks `k`: it runs the checks `1` to `k` of the document and none above. The result says so:
the field `profiles` of the `read_result` (`P7`, "The records") lists, in ascending order of profile and without repeats, one pair
`[profile, k]` for each profile the reader implements. A segment that declares a profile in that list is judged by the checks `1`
to `k`; a file that passes them shows that those checks passed and nothing about a check above `k`. A segment that declares a
profile not in the list is reported `profile_not_checked`. The number `k` satisfies `1 <= k <= n`, where `n` is the
number of checks of the profile document; a reader that runs no check of a profile does not list it; every revision of a
profile document keeps the numbers of the revision before it.

RETIREMENT OF AN ALGORITHM. A registry version can retire an algorithm of any purpose of section 8 by naming it in the column
`retired from` of the table of section 8, in the part that defines the version. Retiring changes the use of an algorithm and
removes no value (`P2-6`). From the registry version `v` that retires it:

- WRITING. A writer does not produce with the algorithm (`P2-95`): no new signature, no segment whose `hash_algorithm` it is, no
  frame whose
  codec it is. A segment whose header declares a registry version of at least `v` and that uses it is not a file that a conforming
  writer produces.
- READING AND VERIFYING. A reader of any version, `v` and later included, still implements the algorithm in full (`P2-10`,
  `P2-96`): it
  checks the links and payloads, decodes, and verifies a signature of the algorithm, with the status and the reason that `P6` and
  `P1` give, as before.
- RELYING. A reader of registry version at least `v` does not treat a signature of a retired algorithm, nor any signature of a
  segment whose `hash_algorithm` is retired, as authenticating (`P6`, 7.2 condition 5): its `authenticated` is `false`. The
  `status` and `reason` of the `signature_result` are those of the verification and do not change; the coverage is computed as
  before; no frame is authenticated through it, so the `authenticity` of the segment is not `authenticated` through it.
- REPORTING. The `signature_result` of a retired algorithm is `[valid or invalid, reason, algorithm, key_id, first, end, false]`;
  no
  finding is added. A valid signature of a retired algorithm under a trusted key therefore shows `status` `valid` and
  `authenticated` `false`, which no other state of a signature gives when the registry version of the result is at least `v`.
- EMERGENCY. A registry version `v` can add no value and only retire; it is accepted and closed as any version is. A reader of a
  version below `v` does not know the retirement, and its result carries its own `registry_version`.

1. `P2-88` A code of a numeric table of this part MUST be assigned by the proposal process of section 9a, at acceptance, and by
   no other party; a proposal MUST NOT assign a code.
2. `P2-89` The assignment log of section 9a MUST hold one row for each accepted proposal that adds, withdraws or retires a value,
   identified by the proposal's identifier, and a row of a closed registry version MUST NOT be edited
   or removed.
3. `P2-90` The codes that two proposals receive MUST be the next integers in the order in which the changes that add them land;
   a proposer, an implementation or a deployment MUST NOT choose a code.
4. `P2-91` A value MUST belong to exactly one registry version, the one named in its row; a closed registry version MUST NOT
   gain, lose or renumber a value; and an implementation MUST NOT claim to conform to a registry version that is open.
5. `P2-92` A value assigned in error in a closed registry version MUST become a withdrawn value and MUST NOT be removed,
   renumbered, reused or given another meaning, and a writer MUST NOT write a withdrawn value from the version that withdraws it.
6. `P2-93` The registry MUST hold no private-use, experimental or reserved-gap range, and a file MUST NOT hold a code that the
   registry does not assign.
7. `P2-94` A reader MUST list in the field `profiles` of its `read_result` each profile it implements with the number `k` of
   checks it runs, MUST run the checks `1` to `k` for a segment that declares it whenever the table STEPS BY ACCESS of `P7` runs
   the checks of that
   profile under the `access` of the read, and MUST NOT run a check above `k`.
8. `P2-95` A writer MUST NOT produce with an algorithm from the registry version that retires it.
9. `P2-96` A reader MUST implement a retired algorithm for reading and verifying, and MUST NOT report `authenticated` `true` for a
   signature of a retired algorithm or of a segment whose hash algorithm is retired, from the registry version that retires it.

## 10. Worked examples

A finding is the record of section 5 encoded deterministically: an array of seven fields, so its head is `87`; `absent` is `81 01`
and `present(v)` is `82 02` followed by `E(v)`; a `uint` below `24` is one byte and one from `24` to `255` is `18` and the byte.

Example 1. Three ordinary frames stand after the committed prefix, the first of them at position `5`. The finding is `[17,
absent, absent, present(5), absent, absent, present(3)]` (code `17` `uncommitted_tail`; the reason, the subject, the offset
and the length are absent by 5.2). Its bytes are `87 11 81 01 81 01 82 02 05 81 01 81 01 82 02 03`.

Example 2. A frame at position `7` stores its payload under codec `2`, which the reader's version does not hold, in a
segment whose header declares a version above the reader's. The finding is `[5, present(1), present([1, 2]), present(7),
absent, absent, absent]`: code `5` `unknown_enumeration_value`, reason `1` `unknown_codec`, subject `codec` (tag `1`) with
the value `2` that the reader did not implement. Its bytes are `87 05 82 02 01 82 02 82 01 02 82 02 07 81 01 81 01 81 01`.
